# HeteroNexus · 异构执行资源决策引擎

> 统一的异构资源决策引擎 —— 在同一套多目标优化内核下，同时覆盖 **算力层**（CPU / GPU / 云 GPU 的作业编排）与 **模型层**（大模型 API / 自建模型的省成本路由）。

**内核保留，场景外扩。** 算力调度回答"这个作业放哪块硬件"，模型路由回答"这个请求调哪个模型"。
两者在数学上是同一个问题 —— 把任务映射到候选执行资源上，在成本 / 延迟 / 质量之间求最优 ——
差别只在一个地方：**质量在算力侧是常量**（训练结果不因节点而变），
**在模型侧是难度的函数**（选错模型就是答错，不可回滚）。这一个差异，就是本项目从 Q1 走到 Q2 的真实技术增量。

## 一、问题背景

高校实验室与中小企业的 GPU 集群普遍存在**算力利用率低、调度不均衡、异构硬件管理复杂**三大痛点：

| 痛点 | 现状 | 后果 |
| --- | --- | --- |
| 队列阻塞 | 静态分配为主，大任务长期占卡 | 小任务排队严重，GPU 平均利用率不足 40% |
| 资源失衡 | GPU 打满但 CPU 闲置（训练任务） | 异构资源无法协同，整体成本高 |
| 管理割裂 | CPU / GPU / FPGA 分别管理 | 缺乏统一资源抽象与调度接口 |
| 优化单一 | 现有方案以启发式规则为主 | 无法同时兼顾延迟、吞吐、能耗与公平性 |

现有方案存在明确缺口：Kubeflow 偏重、部署复杂；NVIDIA GPU Operator 仅支持自家硬件且闭源；Volcano / Kueue 算法以启发式为主，缺乏智能决策层。

## 二、技术方案

系统采用**五层解耦架构**，智能决策层与调度内核层通过 gRPC 通信，支持启发式安全回退：

```
产品与接口层   Web 控制台 · FastAPI · CLI · Helm
      ▼
可观测与管理层 Prometheus · Grafana · OpenTelemetry · 成本核算
      ▼
智能决策层     DRL 调度代理(PPO) · 任务特征提取 · 多目标奖励引擎
      ▼  gRPC
集群调度内核层 K8s Scheduler Framework · Filter/Score/Permit/Reserve · DRA
      ▼
基础设施层     CPU / GPU / FPGA 异构节点池
```

### 核心创新点

1. **多目标奖励塑形**：奖励函数同时建模作业完成时间（JCT）、资源利用率、能耗、公平性与资源碎片率，区别于单一目标的启发式调度。
2. **动作空间扩展**：(任务 → 节点) 联合决策 + "不调度"等待动作 + 抢占动作，而非仅做节点打分。
3. **在线自适应**：DRL 代理根据实时集群状态调整目标权重，解决静态权重无法通吃的帕累托困境（见下方实验结论）。
4. **无侵入部署**：以 K8s 调度插件（而非重写调度器）实现，支持一键回退至 DRF 启发式。

## 四、实验结论

### 4.1 基线算法对比（Python 仿真引擎，seed=42，200 任务）

| 调度算法 | 平均 JCT | 中位 JCT | P95 JCT | 平均等待 | Makespan | GPU 利用率 | CPU 利用率 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| FIFO | 2441.2 | 1720.1 | 9430.4 | 1741.9 | 15231.4 | 94.2% | 46.4% |
| BestFit | 2556.7 | 1911.8 | 9627.2 | 1857.4 | 15323.4 | 93.6% | 46.1% |
| **DRF** | **2094.9** | **786.1** | 10940.9 | **1395.5** | 15498.4 | 92.6% | 45.6% |
| **SJF** | **2018.9** | **713.5** | 10503.8 | **1319.5** | 16172.8 | 88.6% | 43.7% |

**关键发现**

1. 队列排序策略是 JCT 的第一影响因子：DRF 相较 FIFO 平均 JCT 降低 **14.2%**、中位 JCT 降低 **54.3%**。
2. **吞吐与延迟存在明确权衡**：FIFO 的 GPU 利用率最高（94.2%）且 Makespan 最短，但长任务阻塞严重。
3. **长尾任务（P95）是所有基线的共同短板**：DRF/SJF 的 P95 JCT 反而劣于 FIFO —— "短任务优先"会饿死大任务。
4. **CPU 利用率普遍偏低（约 46%）**：异构资源协同存在可观优化空间。

> 结论：固定规则无法同时优化平均 JCT、P95 长尾与 GPU 利用率（三者构成帕累托权衡），这正是引入强化学习动态权衡的动机。

### 4.2 多目标奖励权重敏感性（控制台内置引擎，5 随机种子 × 200 任务平均）

| 权重预设 | w₁ 时间 | w₂ 利用率 | w₃ 能耗 | w₄ 公平 | w₅ 碎片 | 平均 JCT | 中位 JCT | P95 JCT | GPU 利用率 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 均衡（默认） | 0.50 | 0.15 | 0.05 | 0.20 | 0.10 | −16.2% | −43.3% | −3.1% | 89.5% |
| 延迟优先 | 0.70 | 0.05 | 0.05 | 0.10 | 0.10 | **−20.4%** | **−60.3%** | −2.4% | 88.5% |
| 吞吐优先 | 0.20 | 0.45 | 0.15 | 0.10 | 0.10 | −1.2% | −28.2% | −2.2% | **92.2%** |
| 公平优先 | 0.25 | 0.10 | 0.05 | 0.55 | 0.05 | −9.8% | −16.5% | **−4.1%** | 89.7% |
| *参照 SJF* | — | — | — | — | — | −20.5% | −66.1% | −3.5% | 87.7% |
| *参照 FIFO* | — | — | — | — | — | 0.00% | 0.00% | 0.00% | 89.8% |

> 表中百分比为相对 FIFO 基线的变化（负值表示指标更优）。

**三条可复现的发现**

1. **w₂ 与 JCT 存在反向关系**：w₂ 从 0.05 提高到 0.45，GPU 利用率从 88.5% 升至 92.2%，但平均 JCT 改善从 −20.4% 退化到 −1.2%。原因是利用率奖励引导任务向已饱和节点聚集，形成热点并加剧队头阻塞。
2. **无静态权重可通吃全部指标**：四组预设分别落在帕累托前沿的不同位置，不存在支配所有其他配置的单点。
3. **→ 强化学习的必要性**：既然最优权重随负载特征（推理密集 / 训练密集、大任务占比、队列深度）变化，"在线选择权重"本身就是一个可学习的策略，而非调参问题。

### 4.3 场景二：Token 侧路由实验（模型层，Q2 新增）

**要回答的问题**：不知道该用哪个模型的用户，为了保险一律调用最强的那个。这里面有多少是白花的钱？

#### 方法：不烧真实 token 也能验证

整套评估在离线完成，输入只有三样公开可得的东西：

| 输入 | 来源 | 口径 |
|---|---|---|
| 各模型能力分数 | AI Model Benchmark Tracker（2026-04-10） | MMLU / MATH / HumanEval / GSM8K 正确率 |
| 各模型价格 | API 价格汇总（2026-08-17） | 元 / 百万 token |
| 任务难度分布 | 四组可配置的业务场景预设 | 简单 / 中等 / 困难 三档 |

任务能否答对，由 `quality_at_difficulty()` 建模：采用难度校准的 logistic（简化 Rasch/IRT 形式），
保证 **当任务难度等于 benchmark 基准难度时，仿真正确率恰好还原公开榜单分数**。
这条性质让整套数字有了校准锚点 —— 不是凭空造的分布。

#### 结论（mixed 场景，5 份业务流拼接共 10000 任务，GPU 负载率 0.35，λ=0.2）

| 策略 | 总花费 | 省钱 | 正确率 | 质量保有 |
|---|---|---|---|---|
| 全用最强模型（用户现状） | ¥175.89 | — | 90.6% | 100% |
| 全用最便宜模型 | ¥13.43 | 92.4% | 66.6% | 73.5% |
| 级联升级（先小后大） | ¥28.48 | 83.8% | 82.8% | 91.4% |
| **路由方案 · 在线逐任务（λ=0.2）** | **¥78.51** | **55.4%** | **88.9%** | **98.2%** |
| **路由方案 · 离线三档表（可交付形态）** | **¥86.72** | **50.7%** | **89.1%** | **98.3%** |
| 理论最优 Oracle | ¥21.09 | 88.0% | 100% | 110.4% |

**在线逐任务 vs 离线三档表**：前者按每个任务的真实难度与 token 规模实时求解，是效果上界；
后者就是交付给用户的那张 4×3 推荐表，可直接落成一条路由规则。**两者互有胜负，不是上下界关系** ——
在纯 API 候选池下，三档表反而更省（¥60.8 vs ¥69.3）：它按档中点决策，把"升级到强模型"
推迟到了下一个难度档（在线版在难度 ≈0.62 就升级，表要到 0.65），于是少花钱、也略更容易错。
方向取决于候选池结构，因此报告里两个数字都给，只报对自己有利的那个是不诚实的。

**四条可用的结论**

1. **省一半的钱不必牺牲质量**：质量保有 98% 的配置下花掉的钱减半。大多数日常请求用不上顶尖模型。
2. **成本空间的大部分已被简单策略吃掉**（55.4% vs Oracle 的 88.0%），**剩下的差距在质量而不在钱** —— Oracle 既省钱又全对，而实际策略省了钱却掉了 1.7 个百分点。真正的技术难点是"在省钱的同时保住正确率"，这也是 Q2 后续引入强化学习的动机：不是学怎么省钱，而是学怎么省钱还不出错。
3. **"省多少"必须由用户定**：不存在既更便宜又更准的单一方案，只有一条帕累托前沿（见 `figures/token_pareto_front.svg`）。产品的角色是画出这条曲线并标出膝点，而不是替用户决定。**膝点定义带一道闸门**：只在质量保有 ≥95% 的点里选，否则纯几何膝点会推出 λ=0.4（保有 94%）——"便宜 74% 但每 16 个问题多错 1 个"对多数业务是事故而不是优化。加闸门后推荐 **λ=0.3：省 65.7%、质量保有 96.5%**。
4. **结论不是某一批业务流的偶然**：同一策略在 5 份独立生成的业务流上，省钱比例的极差仅 1.2 个百分点（54.8% ~ 56.0%），见 `data/token_experiments.json` 的 `per_sample_spread`。

**省钱幅度高度依赖业务构成**（同样是 λ=0.2，在线逐任务）：

| 场景 | 省钱 | 质量保有 | 说明 |
|---|---|---|---|
| daily_assistant 日常助手 | 62.4% | 97.4% | 简单请求占比高，可省空间最大 |
| dev_copilot 研发 Copilot | 59.2% | 99.8% | 代码任务贵，但强者优势也没那么大 |
| mixed 混合负载 | 55.4% | 98.2% | 默认场景 |
| analytics 分析推理 | 25.7% | 99.1% | 难题占比 45%，**难题本来就省不下来** |

这张表本身就是"要按用户实际业务构成出方案"这一产品立论的依据：同一个用户、同一套模型池，
业务构成不同，能省的钱差 2.4 倍。

#### 算力层与模型层的耦合点

自建模型本质上是用 GPU 卡时换 token，其单位成本反比于 **GPU 有效负载率**：

```
每 token 成本 = GPU 时租金 ÷ 3600 ÷（吞吐 × 负载率）
```

敏感度分析显示临界点在 **20% 负载率附近**：低于此，"自建开源模型替代调 API" 反而不划算。
而"把 GPU 喂满"恰恰是算力侧调度器的职责 —— 两个场景不是并列，是耦合的
（见 `figures/token_utilization.svg`）。

#### 数据溯源与校准

`tokenrouter/data/catalog.json` 中每个模型的能力分数与价格都带来源标注
（`measured` 或 `proxy:xxx`），闭源旗舰缺少同口径公开榜单时用同系列分数代理并显式注明。
GPU 租金与吞吐为工程量级估算，**默认按 0.35 的有效负载率折算**（宁可低估自建的吸引力）。
参数校准后重跑 `python scripts/run_token_experiments.py` 即可刷新全部结论。

**控制台与 Python 端同源**：控制台是零依赖单文件 HTML，Token 侧的全部计算在浏览器里重跑一遍。
两者算法与随机数发生器（mulberry32）逐位对齐，并由 `scripts/verify_console_sync.py` 强制校验
（任务流指纹、5 个策略的花费与正确率、内嵌 catalog 与 JSON 是否一致）。任一侧改动算法都必须
同步另一侧并跑通该脚本 —— 控制台上的数字才能与 README 直接互相引用。

> **口径红线**：对外表述时必须同时给出省钱比例与质量代价。只讲省 92% 而不讲正确率掉到 67%，等同于误导。

### 4.4 场景二进阶：预算约束下的 PPO 路由（Q2 算法增量）

**为什么必须有预算这一维**：4.3 里的问题是「每个请求各花多少」，而任务相互独立时，
「逐任务贪心地最大化 q − λ·cost」**本身就已经是最优解** —— RL 只能把它重学一遍，
拿不出增量。这不是实现问题，是问题定义问题：**没有跨任务耦合，就没有序贯决策**。

真实的耦合来自预算：企业面对的是「这个月就这么多钱，花完就没了」。一旦预算有限、
花完之后剩下的请求无法服务，「这一轮该不该上好模型」就与「后面还剩多少任务、
多少钱」耦合起来 —— 这是背包式的序贯决策，贪心不再最优。

**设定**：每批 150 个任务，预算 = 「全用最强模型跑完这批」花费的 50%。
训练批次取种子 1/7/42，评估批次取种子 999/2026（**与训练不重叠**）。

| 策略 | 答对数 | 服务率 | 花费 | 每元答对数 |
|---|---|---|---|---|
| 全用最强模型 | 1414 | 52.6% | ¥26.48 | 53.4 |
| 全用最便宜模型 | 1961 | 100% | ¥4.05 | 484.4 |
| 逐任务效用贪心（4.3 的路由） | 2639 | 100% | ¥23.19 | 113.8 |
| 预算感知贪心（人均份额内挑最强） | 2648 | 100% | ¥24.42 | 108.4 |
| **PPO（本项目）** | **2567** | **100%** | **¥11.13** | **230.7** |
| PPO 未训练（随机初始策略） | 427 | 18.5% | ¥26.48 | 16.1 |

**结论（两个数字必须一起读）**

1. **PPO 用 46% 的钱拿到了 97% 的答对数**：每元答对数 230.7，是预算感知贪心的 **2.13 倍**。
   它学会的是「把钱花在边际收益高的任务上」，而不是「把预算花光」。
2. **但在「预算必须花光」的口径下，绝对答对数少 3.1%**（2567 vs 2648）。
   这一点必须如实写出 —— 只报每元答对数会让人误以为 PPO 全面占优。
   反过来说，「把预算花光」本身从来不是业务目标：多花 ¥13.3 只多答对 81 题（1.6 题/元），
   而 PPO 在 ¥4 到 ¥11 这段区间里的边际效率是 86 题/元。

> **关于「每元答对数」这一列的读法（重要）**：该指标**单调偏向更便宜的模型** ——
> 上表中「全用最便宜模型」以 **484.4** 居全表之首，是 PPO 的 2.1 倍，但它只答对 1961 题
> （65.4%）。所以本表**不按该列排序**，也不以它作为主结论。真正可比的是**固定预算下的
> 帕累托位置**：在 ¥11.13 这一花费水平上，没有任何基线能达到 2567 题（最接近的
> 「全用最便宜模型」只有 1961 题）。PPO 的定位是**帕累托前沿上一个效率优先的工作点，
> 而不是任一单项指标的最优解**。

学习本身确实发生了：随机初始策略只答对 427 题（服务率 18.5% —— 它把预算一次性花光就结束了），
训练后 2567 题，**提升 6.0 倍**。

**实现说明**：PPO 为纯 NumPy 手写实现（`tokenrouter/ppo.py`，含 GAE、裁剪代理目标、
熵正则、Adam、全局梯度裁剪）。不引 torch 的理由是可复现性优先 —— 自实现只有一个随机源，
而大型框架会带进 cuDNN 非确定性与多线程归约顺序等不可控因素；且 10 个离散动作、
9 维状态的小问题在 CPU 上几十秒即收敛。代价是这部分需要 numpy，已单独成测试文件
（`tests/test_rl_routing.py`），在没有 numpy 的环境里整组跳过，不影响零依赖部分。

> **踩过的坑（保留为记录）**：`grads()` 最初把策略项的符号写反、漏了 `ratio` 因子、
> 熵项写成 −p·(log p + 1)（应为 −p·(log p + H)）。症状是训练曲线单调下行、
> 智能体越学越差。`tests/test_rl_routing.py::TestPPO::test_训练后优于未训练` 是它的回归网。

### 4.5 场景二进阶：Token 消耗数字孪生（时间 + 容量 + 排队）

**为什么需要它**：4.1–4.4 的仿真**没有时间维度** —— 给它 11 万个任务，逐条路由、
最后汇总，任务之间没有先后、也不会互相抢资源。而方案落地时最先撞上的墙恰恰是
时间性的：这一分钟烧掉多少 token、什么时候撞上供应商的 TPM / RPM 配额、
便宜的自建模型容量有限时高峰期溢出到哪去。这几件事批量仿真一个都回答不了。

**它是什么**：一个**离散事件仿真**（`tokenrouter/twin.py`）—— 请求按到达过程进入
系统，每个后端有 TPM / RPM 配额与并发上限，占满则排队，排队超过 `wait_timeout`
即丢弃。沿用「数字孪生」这个说法，指的是它具备孪生的三个特征：**有状态**、
**随时间演化**、**可注入策略并返回系统级的动态响应**；但它是一个**模型**，不是
对真实系统的测量 —— 没有真实系统可校验，这一点在答辩时不能含糊。

**设定**：一个工作日（8 小时），mixed 场景，基准 150 req/min（叠加时段系数与突发
后峰值约 231 req/min），共 **110,641** 个请求，配额档位 team。

| 策略 | 成功服务 | 服务率 | 每千次成功服务 | 超时丢弃 | 排队率 |
|---|---|---|---|---|---|
| 全用最强模型 | 95,486 | 86.3% | ¥17.57 | 15,155 | 76.8% |
| 全用最便宜模型 | 50,022 | **45.2%** | ¥1.34 | **60,619** | 100% |
| 级联（先便宜后升级） | 87,317 | 78.9% | ¥3.35 | 23,324 | 70.2% |
| **难度路由（本项目）** | **110,641** | **100%** | **¥7.89** | **0** | 0.5% |
| 离线方案表 | 110,641 | 100% | ¥8.67 | 0 | 2.1% |

**结论（三条，按能被反驳的程度排序）**

1. **「全用最便宜模型」在容量约束下不成立**：它只服务了 45.2% 的请求，
   把 **60,619 个**请求排死在队列里。原因是便宜的自建模型 `tpm_limit` 由
   `throughput_tps` 推导 —— **越便宜的自建模型容量越小**：9B 在 team 档只有
   132k TPM（约 100 req/min，不到到达峰值 231 的一半），72B 更是只有 31.2k TPM。
   省钱方案撞到的第一堵墙不是价格，是配额。
2. **难度路由同时赢得服务率与单价**：在配额充足的档位（enterprise / unlimited，
   两者都能服务满）下，每千次 ¥7.89 vs 最强 ¥17.57，**省 55.1%**；在 team 档
   最强服务不满（86.3%）时，难度路由既多服务 13.7 个百分点的请求、单价还便宜 55%。
   它几乎不排队（排队率 0.5%），因为它天然把流量摊到了多个后端上。
3. **配额不足时，多服务一个请求是要付钱的**：startup 档下难度路由只能服务 31.0%
   （¥6.45/千次）；打开容量感知的二次路由（`--overflow reroute`）后服务率升到
   **55.5%**，但每千次涨到 **¥29.38** —— 溢出到贵的商用模型上去了。

> **读这张表时必须避开的坑**：排队超时与预算耗尽的请求**既不算花费也不算答对**，
> 于是「把请求丢掉」在账面上永远最省钱（上表「全用最便宜模型」的 ¥1.34 就是这个
> 陷阱）。所以本表**从不单独引用总花费**：一律把**服务率**与**每千次成功服务的
> 花费**并列；`run_twin.py` 里的省钱比例只在**服务率 ≥ 99% 的策略之间**比较，
> 低于门槛的策略会单独列出并标「其总花费低主要来自丢请求」。

**正确性锚点**：把配额设成无穷（`--tier unlimited`），时间、排队、限流全部失效，
孪生必须**逐位退化**为批量仿真 `engine.run_policy` 的结果 —— 花费与答对数完全相等。
由 `tests/test_twin.py::test_无容量约束时退化为批量仿真` 对全部 6 个策略守住。
没有这条锚点，「服务率只有 45%」可能只是仿真 bug。

**控制台同源**：孪生引擎在浏览器里也实现了一份（`console/index.html` 的
「Token 消耗孪生」页签），`scripts/verify_console_sync.py` 逐位比对 8 组配置。
为此到达过程**刻意不用泊松**（指数间隔需要 `-ln(u)`，而 `Math.log` 在 JS 与 Python
之间不保证逐位一致），时段系数用**查表**而非 `sin`，取整用 `int(x+0.5)` 而非
`round()`（Python 是银行家舍入 `round(202.5)=202`，JS 是 `Math.round(202.5)=203`，
而 `150×1.35=202.5` 会真实出现）。

### 4.6 孪生环境里的 PPO：预算 + 实时容量双重约束（Q3 算法部分提前）

4.4 的耦合只有预算一层；4.5 证明了容量是省钱方案最先撞上的墙。这一节把两者
放进同一个决策问题：智能体既要看「钱还剩多少」，也要看「哪些后端此刻有空位」，
还得看「这个任务有多难」。环境为 `tokenrouter/twin_env.py`，脚本
`scripts/run_twin_rl.py`。

**设定**：startup 档（配额与预算同时咬紧的区间 —— team 档下容量几乎不紧张，
问题会退化成 4.4 那个纯预算问题），60 req/min，每段片段 300 秒（约 390 个请求），
预算 = 「这段流量全交给最强模型」的 50%，λ=0.2，PPO 训练 300 轮。
评估用 6 段**训练未见过的**片段（种子 999/2026）。

| 策略 | 服务数 | 服务率 | 答对数 | 花费 | 每千次 | 超时丢 | 超预算丢 |
|---|---|---|---|---|---|---|---|
| 容量感知贪心 | 1911 | 71.8% | **1634** | ¥22.67 | ¥11.86 | 117 | 633 |
| **PPO（本项目）** | 1909 | 71.7% | 1597 | ¥22.49 | **¥11.78** | **106** | 646 |
| 效用贪心（看不见容量） | 1468 | 55.2% | 1343 | ¥12.28 | ¥8.37 | **1193** | 0 |
| PPO 未训练（随机初始） | 921 | 34.6% | 747 | ¥23.38 | ¥25.39 | 105 | 1635 |
| 全用最强模型 | 383 | 14.4% | 355 | ¥6.56 | ¥17.12 | 2278 | 0 |
| 全用最便宜模型 | 179 | 6.7% | 113 | ¥0.23 | ¥1.27 | 2482 | 0 |

**结论（三条，包括没赢的那条）**

1. **学习确实发生了**：随机初始策略只答对 747 题（服务率 34.6%，它把预算一次性
   花光就结束了），训练后 **1597 题（+114%）**，服务数 921 → 1909，而花费略降。
2. **容量感知是这一节真正的增量**：看得见「此刻有没有空位」的贪心比看不见的
   服务率高 **+16.6 个百分点**（71.8% vs 55.2%），答对多 291 题；看不见容量的
   贪心把 **1193 个**请求排死在队列里，看得见的只丢 117 个。**这个问题只有孪生
   问得出来** —— 批量仿真里根本没有「此刻有没有空位」这个状态。
3. **PPO 没赢过容量感知贪心**：答对 1597 vs 1634（**−2.3%**），服务率与花费
   基本持平。这一条如实写在这里：**在「有空位就在可用集合里按效用挑」这一层，
   固定 λ 的贪心已经接近最优**；RL 的增量本应来自预算的跨时间分配，而本档位下
   预算不是主要瓶颈（超预算丢 646 vs 排队丢 106）。只报赢的那半边是造假。

> **踩过的坑（保留为记录）**：决策函数一度返回的是**下标**而不是模型 id，
> `_Sim` 会静默回退到「第一个可用后端」，于是训练好的网络与随机初始网络在评估
> 里跑出**逐位相同**的结果，而训练曲线明明在涨。现在 `evaluate_twin_agent` 对
> 非 id 的返回值直接抛 `ValueError`，并有回归测试盯着。

pip install -r requirements.txt

### 打开调度控制台

控制台为**单文件、零依赖、完全离线**的 HTML，直接双击即可：

```bash
# Windows
start console/index.html
# macOS
open console/index.html
```

控制台提供 7 个页签：实时调度数字孪生、基线实验基准、系统架构、年度路线图、工程能力图谱、
**模型路由方案**、**Token 消耗孪生**。前五个为算力侧，「实时调度数字孪生」页可热切换调度
算法、调节多目标奖励权重，并现场记录对比结果生成帕累托表；「模型路由方案」页可拖 λ 滑块
实时看省钱比例与质量代价，并给出按（能力域 × 难度档）的可交付推荐表；「Token 消耗孪生」页
可调节配额档位、到达率与突发强度，实时看到**花费曲线、队列深度、token 速率与逐后端用量**，
并直接给出每个策略的服务率与「每千次成功服务的花费」—— 全部计算在浏览器内完成，
与 Python 端逐位一致（8 组配置由 `verify_console_sync.py` 强制校验）。

### 运行测试

```bash
pytest tests/ -v      # 99 项：算力侧 40 项 + Token 侧 59 项（含 RL 16 项）
```

### 场景二：Token 侧路由评估（模型层）

```bash
# 混合候选池（商用 API + 自建开源模型），推荐默认 λ=0.2
python scripts/run_token_experiments.py

# 只看商用 API —— 模拟没有自建 GPU 的个人 / 小企业用户
python scripts/run_token_experiments.py --api-only

# 切换业务场景：daily_assistant（轻量）/ dev_copilot（研发）/ analytics（高难度）
python scripts/run_token_experiments.py --scenario dev_copilot

# 调节省钱力度：λ 越大越省钱、质量相应下降
python scripts/run_token_experiments.py --cost-weight 0.4

# 自建 GPU 负载率敏感性（默认 0.35；设为 1.0 会显著低估自建成本）
python scripts/run_token_experiments.py --gpu-utilization 1.0

# 生成图表 → figures/token_*.svg
python scripts/generate_token_charts.py

# 导出可执行的方案文件（YAML），并当场验证「装回执行」与策略一致
python scripts/export_plan.py --scenario dev_copilot --out plans/plan_dev.yaml

# 预算约束下的 PPO 路由（需要 numpy）
python scripts/run_rl_routing.py --budget 0.3

# Token 消耗数字孪生：时间 + 容量 + 排队（默认 8 小时工作日，team 档）
python scripts/run_twin.py
python scripts/run_twin.py --tier startup                # 配额最紧的一档
python scripts/run_twin.py --overflow reroute            # 容量感知二次路由
python scripts/run_twin.py --budget 500                  # 加预算约束

# 孪生环境里的 PPO：预算 + 实时容量双重约束（需要 numpy，约 1 分钟）
python scripts/run_twin_rl.py
python scripts/run_twin_rl.py --tier team                # 容量不紧张时会退化成纯预算问题

# 校验控制台（浏览器内 JS）与 Python 端是否仍然逐位一致
python scripts/verify_console_sync.py
```

结果写入 `data/token_experiments.json`：策略对比、帕累托前沿、可交付推荐表、
跨业务流离散度、GPU 负载率敏感性分析，以及全部数据的来源标注。
